# 判据：软约束 / 硬约束 / 红线怎么分

扫完门禁后逐条分类。**判不清就标"待问"，不要硬分。**

## 三个类别的定义

| 类别 | 管的是什么 | 可验证吗 | 本技能的动作 |
|---|---|---|---|
| **软约束**（判断型） | 想不想得明白 | 不可验证，需要语义判断 | **可软化**，改成判断式 |
| **硬约束**（承诺型） | 对外承诺、流程必需 | 可验证或可证伪 | **保留**，补"何时不适用" |
| **红线** | 不可触碰 | 可验证，且有明确严重后果 | **保留原样**，不动 |

## 怎么区分软和硬：三个试金石

**试金石一：换个问法。** 把"不许 X"换成"如果 X，会发生什么"。
- 能自然接出原因的 → 它是软的（它本来就是判断）。
- 接不出原因，只能说"就是不行" → 它是硬的，往红线/承诺查。

**试金石二：看代价。** 违反它的最坏结果是什么？
- 最坏是"写得平庸"、"少一个增量" → 软的。
- 最坏是"读者按钩子找过来、交付物不存在，一次就伤信用" → 硬的。
- 最坏是"不可逆的损失" → 红线，且应该考虑移到执行层。

**试金石三：看有没有唯一正确答案。**
- 多种写法都行，只是有好坏 → 软的，给判据。
- 只有一种做法对，其余全错 → 硬的，而且**很可能根本不该写在提示词里**（该写进脚本）。

## 边界案例（实战中真实踩到的）

### 案例一：钩子必须有真实交付物

原文：「**硬约束：每条钩子背后必须有真实存在的交付物。**没有真东西的钩子是一次性加粉。」

**判定：硬约束，保留。** 它是对外承诺，不是风格问题。

**但它缺边界，要补**：硬约束管"有没有"，不管"火候到没到"。有真交付物但只做到一半，不算违规——写进建议书的"我不确定的地方"交人决定。**不要因为火候不够就把有真东西的钩子否掉。**

### 案例二：删除文件 / 动资金 / 对外发送 / 改生产环境

原文常写作「**严禁**直接删除…」「必须备份后才能…」。

**判定：不可逆操作，不软化。** 官方立场：这类操作不能只靠模型自己判断，必须严格定义（网址见 `官方依据.md` 第 6 条）。

**正确动作不是软化，是搬家**：建议把这条从提示词移到 permissions / sandbox / hooks / 代码层。理由是：写在提示词里的约束，无论写多硬，本质都是软的——它依赖模型选择遵守。

### 案例三：流程型硬约束

原文：「OCR 四项确认门禁未通过禁止动笔；配图 ≥5 张不许例外。」

**判定：流程型硬约束，判断点不在"软硬"，在"这个约束还成不成立"。**

**要问的是：它防的坏结果现在还发生吗？**
- 还发生 → 保留，并且优先考虑搬家到脚本（图片数量这种可数的事，本来就该用代码校验）。
- 模型现在已经不会犯 → 这是可以整条删的，官方自己就是这么干的（删掉 80% system prompt，测评无损，网址见 `官方依据.md` 第 2 条）。

**这一条最重要**：老 skill 里很多硬门禁，真正的死因不是"太硬"，是"过期"——它防的失败模式早就不发生了，但没人删它，于是继续争夺注意力预算。

### 案例四：关于同一个词，内地和香港是两个客群

原文：「**不排除别的市场**｜同一个词，内地和香港常常是两个完全不同的客群，混着读结论一定错。」

**判定：软约束，但已是合格形态，不要动。**

判据：它给的是后果（"结论一定错"），不是禁令。模型读到的是机制，不是命令。这类"禁令 + 理由"的条目，本技能只删禁令二字，理由留着。

## 一条容易搞反的判定

**"不许'别慌'"这类是软约束，不是硬约束。**

它虽然用了"不许"，但它约束的是**文章风格**（写给读者的内容），不是 Agent 行为。本技能只处理后者。判断方式：这条规矩是管 Agent 怎么做，还是管 Agent 产出的内容长什么样？
